# Pilot: an account-manager assistant that remembers

The current Pilot sends one model call with a system prompt and recent chat history, so it forgets anything that no longer fits. This repository replaces that with an **account notebook**. Every message is logged per user. A cheap helper model *proposes* notes (contacts, preferences, dated facts, follow-ups) and code *validates* them. Each reply's prompt is then rebuilt from what matters for the accounts in play, under a token gate that keeps every reply call at or below 8,000 input tokens.

- **Why and how:** [`DECISIONS.md`](DECISIONS.md) covers the diagnosis, the rules, the alternatives and what breaks first.
- **Every assumption:** [`ASSUMPTIONS.md`](ASSUMPTIONS.md).
- **Results:** the summary below, and the full reports `results/runs/final/report.md` (all five variants), `results/runs/final2/report.md` (`b1`, `lex` and `new` after the fixes the first run exposed), `results/runs/final3/report.md` (`new` after one more fix), `results/runs/baseline/report.md` (the baseline phase) and `results/judge_audit/audit.md`.

**Headline (k = 1).**
- **Six weeks of realistic use:** `new` passes **6 of 7** probes; the brief's baseline (`b0`) passes **1 of 7**.
- **Short scenarios,** where the whole history still fits in 8k: they are level, **31 vs 30 of 34** probes.
- **All suites except the window sweep (41 probes):** `new` **90%**, `b0` 76%.
- **Cost and speed:** `new` sends 53% fewer input tokens per reply (2,632 vs 5,642 on average), but replies in 4.0 s against 1.5 s, because its extraction call runs synchronously.
- **Cap:** every reply stayed at or below 8,000 input tokens.

## Repository map

| `pilot/extract.py` | The helper call that proposes notes, and the validators V1–V6 that decide what is stored. |

| `pilot/baselines.py` | The current Pilot, built for comparison: `v0` (current session only), `b0` (the brief's baseline: newest-first history up to 8k) and `b1` (`b0` plus our grounding rules). |
| `pilot/prompts/` | Every prompt, in plain text. |
| `eval/` | The replay harness, LLM judge, judge audit and report generator, plus `PREDICTIONS.md`, which was written before our system's results existed. |
| `scenarios/` | `samples/` (our reconstructions; the attached originals never arrived), `holdout/` (paraphrased siblings and grader-style scenarios, not used for tuning; the two exceptions are recorded in ASSUMPTIONS A1), `own/` (`own_01`-`05` one per complaint, `own_06` a replaced fact, `own_07`-`08` interface rules, `own_09`-`12` aimed at our own design's weaknesses), `long/` (6 weeks of realistic use), `sweep/` (the same fact behind 0 to 320 messages). `INDEX.md` explains each one. |
| `results/` | Generated by the commands below and never edited by hand: `runs/<tag>/` for each evaluation run (`runs/baseline/`, `runs/final/`, `runs/final2/`, `runs/final3/`) and `judge_audit/` for the judge audit. |

## Setup

Requires Python 3.11 or newer.

```bash
python -m venv .venv
# Windows: .venv\Scripts\activate     macOS/Linux: source .venv/bin/activate
pip install -r requirements.txt
```

Set your OpenRouter key in the environment variable named by `api_key_env` (default `OPENROUTER_API_KEY`):

```bash
export OPENROUTER_API_KEY=sk-or-...        # PowerShell: $env:OPENROUTER_API_KEY = "sk-or-..."
```

For the eval scripts you can instead put the line `OPENROUTER_API_KEY=...` in a `.env` file at the repo root: they load it (it is already in `.gitignore`). `pilot` itself never reads `.env`. When you use `Assistant` directly, the variable must be set in the environment. It is read at every call, with stray whitespace stripped.

## Using the assistant

```python
from datetime import datetime
from pilot.assistant import Assistant

bot = Assistant("data/", {"model": "qwen/qwen3.7-flash", "api_key_env": "OPENROUTER_API_KEY"})
bot.start_session("u1", "s1", datetime(2026, 3, 2, 9, 10))
reply = bot.chat("u1", "s1", "Just off a call with Acme. Their CFO, Dana Ruiz, wants one-page proposals.", datetime(2026, 3, 2, 9, 11))
print(reply.text, reply.input_tokens)   # input tokens of that reply call: the provider's count (our own count if it sent none; 0 if no call was made)
bot.end_session("u1", "s1", datetime(2026, 3, 2, 9, 14))   # optional: nothing is lost if it is never called
```

All state lives under `data_dir`, so a new `Assistant` on the same directory carries on where the last one stopped:
- `users/<hash>.sqlite`, one database per user;
- `usage.jsonl`, one line per completed model call;
- `token_calibration.json`, the learned token factor (only once a count has had to be raised);
- `prompts.jsonl` and `extract.jsonl`, written only when `log_prompts` is on.

Time comes only from the `ts` arguments. Call `bot.close()` before deleting `data_dir`. On Windows, open SQLite files cannot be deleted.

### Configuration

Only `model` and `api_key_env` are required. Every other key has a default.

| Key | Default | What it does |
|---|---|---|
| `model` | `qwen/qwen3.7-flash` | OpenRouter id of the model that writes the user-facing reply. It is set in config rather than code, so the graders can run with their own key and model. |
| `api_key_env` | `OPENROUTER_API_KEY` | Name of the environment variable that holds the key. The key itself never appears in config, code, logs or error messages. |
| `base_url` | `https://openrouter.ai/api/v1` | Any OpenAI-compatible API root. Requests go to `<base_url>/chat/completions`. The OpenRouter-only fields (`usage`, `reasoning`, `provider`) are sent only when this is openrouter.ai. |
| `helper_model` | `None` (= `model`) | Model for the background helper (note extraction). Helper calls do not count toward the reply cap. |
| `memory` | `full` | `full` is the complete design. `lex` is the same system without the extractor, used to measure what extraction adds. |
| `llm` | `openrouter` | `fake` swaps in `FakeLLM`: no network, no cost. |
| `max_input_tokens` | `8000` | The brief's hard cap. A reply prompt is never sent above it. |
| `target_input_tokens` | `7400` | What the prompt builder aims for using our local count. The margin absorbs any difference between our count and the provider's. |
| `reply_max_tokens` / `helper_max_tokens` | `900` / `1500` | Output caps. At 700, a few helper answers on long messages were cut off mid-JSON. |
| `temperature` / `seed` | `0.3` / `7` | Sampling settings for replies. The seed is sent on every call. |
| `reasoning` | `False` | Sends `reasoning={"enabled": false}`. If a model requires reasoning, the call is retried once without the field. |
| `request_timeout_s` / `max_retries` | `60` / `3` | Timeouts, dropped connections, HTTP 408, 429 and 5xx (also when reported inside a 200 body) are retried after 2, 4, then 8 s. |
| `log_prompts` | `False` | Writes every reply prompt to `<data_dir>/prompts.jsonl`. The eval turns this on to check whether the needed fact reached the prompt. |
| `provider` | `None` | Optional OpenRouter provider-routing object, passed through unchanged. |

## Running the samples

```bash
python -m eval.run --tag samples --variants new --scenarios "scenarios/samples/*.jsonl"
```

This replays each file through the interface (honouring `restart` events), judges every probe, and writes `results/runs/samples/report.md`. Add `--no-judge` to replay only. Add `--fake` to run fully offline: FakeLLM replies and a fake judge, no API calls. That checks the pipeline but produces no result.

## Running the evaluation

```bash
python -m eval.run --config eval/config.json --tag final      # all variants x all scenarios, then judge, then report
python -m eval.audit                                           # judge audit: known-good / known-bad replies per probe
python -m eval.report --tag final                              # rebuild the report from the saved events and judgments
```

- **What it runs:** every scenario in `eval/config.json` against all five variants: `v0`, `b0`, `b1`, `lex` and `new`.
- **Rerunning:** an existing tag is never overwritten, so give a rerun a new tag (for example `--tag rerun`). `eval.audit` keeps its verdicts in `results/judge_audit/audit.jsonl` and re-judges only cases it has not seen; move that file away to audit from scratch.
- **Seeds:** reply seed 7, plus the repetition index. The judge's votes use seeds 12, 13 and 14 (`judge_seed` 11 plus the vote number).
- **Judge:** `z-ai/glm-5.3-flash`, a different model family from the reply model, with three votes per probe and the majority winning. We first used `z-ai/glm-5.3`, but its long mandatory reasoning cost up to ten times as much per judged reply ($0.0015 to $0.031 measured, against $0.0003 to $0.0005 for Flash), which the $5 budget could not carry. The judge audit (`python -m eval.audit`) measures how often Flash gets known answers right.
- **Spend guard:** the run stops starting new jobs once *this run* has spent `max_spend_usd`, measured as the growth of the key's usage since the run started.
- **Interrupted runs:** `python -m eval.run --resume final` keeps the cleanly finished jobs, re-runs the rest from scratch and then judges. `python -m eval.judge --tag final` only judges probes that have no verdict yet. Replies that never came from the model (the provider failed after its retries) are flagged, never judged, and mark the run incomplete until it is resumed.
- **What gets saved under `results/runs/<tag>/`:**
  - every event's reply, `input_tokens`, latency and needle check;
  - each job's usage totals (`usage/<job>.json`). The per-call logs, prompts and SQLite files stay under `data/`, which is git-ignored because of its size;
  - the judgments;
  - a `run_meta.json` with the code and prompt hashes.

Reruns will not match token for token, because providers do not guarantee determinism even with a seed. We ran k = 1 repetition (the day's budget was $5), so the report cannot show run-to-run spread. It lists every probe's result so a rerun can be compared probe by probe.

## Results

Three runs over the same 36 scenarios, with the same models: `qwen/qwen3.7-flash` for replies and the helper, `z-ai/glm-5.3-flash` as judge (3 votes), k = 1. Each variant is reported from the last run that measured its current code:
- **`results/runs/final/`:** all five variants. `v0` and `b0` are reported from here, because they use none of the files changed later.
- **`results/runs/final2/`:** `b1`, `lex` and `new` again, after the fixes the first run exposed (see below). `b1` and `lex` are reported from here.
- **`results/runs/final3/`:** `new` alone, after raising the helper's output cap (item 4 below). Only `new` uses the helper.

| Variant (run) | All suites except sweep (41 probes) | Samples + holdout (17) | Own (17) | Long-horizon, 6 weeks (7) | Window sweep (8) | Reply input tokens, mean / max | Cost, replies + helper | Median `chat()` latency |
|---|---|---|---|---|---|---|---|---|
| `v0` (final) | 4/41 (10%) | 2/17 (12%) | 2/17 (12%) | 0/7 (0%) | 0/8 (0%) | 395 / 7,646 | $0.072 | 1.13 s |
| `b0` (final) | 31/41 (76%) | 15/17 (88%) | 15/17 (88%) | 1/7 (14%) | 4/8 (50%) | 5,642 / 7,646 | $0.531 | 1.53 s |
| `b1` (final2) | 29/41 (71%) | 14/17 (82%) | 14/17 (82%) | 1/7 (14%) | 3/8 (38%) | 5,796 / 7,667 | $0.545 | 1.52 s |
| `lex` (final2) | 32/41 (78%) | 13/17 (76%) | 14/17 (82%) | 5/7 (71%) | 7/8 (88%) | 1,821 / 3,662 | $0.202 | 1.28 s |
| **`new` (final3)** | **37/41 (90%)** | **16/17 (94%)** | **15/17 (88%)** | **6/7 (86%)** | **7/8 (88%)** | 2,632 / 5,278 | $0.494 | 3.97 s |

- **Calls:** each variant made 2,896 reply calls. `new` also made 2,896 helper calls (4.24M input and 0.65M output tokens), which do not count toward the cap. The largest provider-reported reply prompt was 7,667 tokens.
- **Per-scenario and per-probe results, the failure funnel and needle reach** are in the two reports.
- **With k = 1 a single probe moves the headline by 2.4 points,** so differences of a probe or two on the short suites are noise. The long-horizon and sweep gaps are not.

**What the numbers say**

- **While history fits in 8k, the baseline is strong.** Replies average about 70 tokens, so `b0`'s window holds one to three days of use. On the short suites `b0` and `new` are level: 30 and 31 of 34 probes.
- **Past that, `b0` loses the fact.** It passes 1 of 7 probes on six weeks of use and 4 of 8 on the sweep, against 6 of 7 and 7 of 8 for `new`. The failure funnel shows these are window misses, the needed fact absent from the prompt. `new` had every needle phrase in its prompt for 42 of 43 probes.
- **Grounding rules alone do not fix memory.** `b1` scores 71% overall and 1 of 7 on the long suite. They do change how the model fails. Given the same missing context in `own_02`, `b0` answered *"The Globex renewal is in October"*, which was Litware's month, while `b1` answered *"I don't have the Globex renewal date on record"*.
- **The judge was checked.** On 196 known-answer controls, GLM 5.3 Flash agreed every time, and every vote was unanimous:
  - gold replies pass;
  - wrong and empty replies fail;
  - "not on record" passes only where abstaining is right.

  The controls are clear-cut, so we also read the failing replies by hand.

**Where the baseline ties or wins**

- **`own_09`, paraphrase** ("relocating" vs "moving the head office"): keyword search misses it, while `b0` has it in its window. `new` failed it in `final` and `final2`, and passes in `final3` only because its note about the move is now stored (item 4). Anything not captured in a note stays a designed weakness.
- **`own_11`, "resend yesterday's draft":** `new` never stores Pilot's replies, so it re-drafts from the user's request. Also a designed weakness.
- **`sample_03`:** `new` answered *"Nothing on record mentions Globex."* That is correct, but it did not offer to note it, which the probe requires. The model does not always add the offer; it did in an earlier smoke run.
- **`sweep_00`:** `new` asked for the migration status instead of drafting with placeholders. Some over-caution remains.
- **`long_01` and `own_10`:** lost on 2–1 votes. `long_01` had no price on record and named it as missing; `own_10` listed the right two accounts plus a hedged third.
- **Latency:** always. `new` waits for its extraction call; moving that to a background worker would remove most of the gap.

**What the first run taught us (the changes between `final` and `final2`)**

1. **The helper closed notes it should not have,** across accounts and on progress updates:
   - *"Relecloud too: Amara takes over UAT approvals from Ben"* closed a Litware contact;
   - *"9 of 12 seats active"* closed *"the pilot kicked off yesterday"*.

   V5 now lets a message close only the notes of the accounts it names, and closes a contact only when the message names that person. That code rule stops the cross-account close. The progress-update close is countered only by the helper prompt, which the model can still ignore: in `final2` one wrong close still got through, in `own_05`.
2. **Closed notes lost their computed date,** so the model hedged on when that pilot started. They keep it now.
3. **Our grounding rule (v2) made the model over-cautious.** `b1` scored below `b0` (63% vs 76%). Its six lost headline probes:
   - a refused draft;
   - two "not on record" answers without the offer to note it;
   - a bare answer;
   - an extra account listed;
   - one window miss.

   v3 says:
   - draft at once, with every known fact filled in and placeholders for the rest;
   - answer with the person's role and what changed.

   We checked it on the dev suites first (own and samples: `new` 15 → 17 of 20, before the V5 change). In `final2` it lifted `new` from 78% to 88%, `lex` from 73% to 78% and `b1` from 63% to 71%.

   **The holdouts were not blind for `final2`.** No scenario file changed between the runs, but the failure analysis read `new`'s holdout failures (`gs_02`, `gs_03`, `gs_04`) before the fixes. The blind holdout figure is the first run's: `new` 11/14, `b0` 12/14.
4. **Found after `final2`:** 5 of the 2,896 helper answers had been cut off at the 700-token output cap mid-JSON, so those messages left no notes. One was `own_09`'s relocation message. `helper_max_tokens` is now 1,500. Re-measured in `final3`:
   - extraction failures fell from 5 to 1;
   - `own_09` and `gs_02` #0 now pass;
   - `own_10` and `sweep_00` flipped the other way (k = 1);
   - `new`'s headline went from 88% to 90%.

**Compared with [`eval/PREDICTIONS.md`](eval/PREDICTIONS.md)** (written before any `lex` or `new` result existed)

- **Right:**
  - `b0` and `b1` have the highest token counts;
  - `new` is the slowest;
  - no reply goes over 8k;
  - `new` beats `b0` on `own_02`, `sweep_40` and the long suite;
  - `b0` ties or beats `new` on `own_09`, `own_11` and `own_12`.
- **Wrong:**
  - We expected the samples' and holdouts' facts to fall out of `b0`'s window. With 70-token replies they did not, so `b0` passed most of them. That is why we built the long-horizon suite.
  - We expected the order `new ≥ lex > b1 > b0 > v0`. It came out `new > lex > b0 > b1 > v0`.
