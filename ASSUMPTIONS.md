# Assumptions register

The brief leaves gaps on purpose ("Make an assumption, state the reason behind it, and carry on"). This file lists **every** assumption we made, and the behavioural rules that rest on one. Each entry gives the assumption, why we chose it, and what would change if it turned out to be wrong. Where an entry names a file or a function, the code is the reference. `DECISIONS.md` summarises the ones that shape the design. The full list is kept here so that DECISIONS stays within three pages. Numbers are never reused: new entries go at the end of their section, and an entry that stops holding is marked withdrawn.

## B. Provider, models, tokens and cost

| # | Assumption | Why | If wrong |
|---|---|---|---|
| B1 | **The provider is OpenRouter**, through its OpenAI-compatible `/chat/completions` endpoint. The graders run it with their own OpenRouter key: `config = {"model": "...", "api_key_env": "OPENROUTER_API_KEY"}`. | The brief allows "any provider and model" and reruns our code "with our own key for the same provider". OpenRouter offers cheap open-weight models and returns each call's token counts and cost, which lets us report spend exactly. | Another OpenAI-compatible API needs only a `base_url` change: the OpenRouter-only body fields (`usage.include`, `reasoning`, `provider`) are sent only when the host is openrouter.ai (`pilot/llm.py: is_openrouter`). There, cost reads $0 (no `usage.cost`), the eval's spend guard (which reads OpenRouter's `/key`) never trips, and reasoning is not switched off. A provider that is not OpenAI-compatible needs a new client in `pilot/llm.py` with the same `complete()` signature. Nothing else changes. |
| B2 | **Replies use `qwen/qwen3.7-flash` with reasoning disabled** (`reasoning={"enabled": false}`). | The day's budget was $5. One evaluation pass replays 2,896 `chat()` calls per variant (36 scenario files), 14,480 for the five variants, plus helper and judge calls. When we built, this was among the cheapest capable models on OpenRouter ($0.03 per million input tokens, $0.13 per million output). Reasoning off keeps chat fast and cheap. | A stronger model would raise every variant's absolute pass rate. The comparison stays fair because every variant uses the same model, but absolute numbers will not carry over to other models. A model that refuses to switch reasoning off is retried once without the field and remembered, so it still works, at its own speed and cost. |
| B3 | The helper (extraction) model defaults to the reply model. `helper_model` overrides it. Helper calls run at temperature 0 in JSON mode, with at most 1,500 output tokens each (700 until after `final2`, when 5 of 2,896 answers turned out to be cut off mid-JSON on long messages). A message over 2,500 tokens is extracted in parts of about 1,800 tokens, in at most 6 calls. | One model means one dependency, one tokenizer and one bill. One answer is capped, so a long paste in a single call would lose its end or break the JSON. | A stronger helper would probably propose more and better notes; the validators stay the same. That is a pure config change. |
| B4 | **Our judge is `z-ai/glm-5.3-flash`** ($0.12/M input, $0.38/M output), a different model family from the reply model. Each reply gets 3 votes (vote 1 at temperature 0, votes 2 and 3 at 0.7, seed `judge_seed` + vote) and the majority wins. Reasoning stays on (no reasoning field is sent). We started with `z-ai/glm-5.3`, but its mandatory reasoning made a probe cost about $0.005 live (3 votes), too much for the $5 day once the audit and the baseline judging are counted. | Using a different family avoids a model grading its own style. Three votes reduce variance. The brief grades with an LLM judge too, but we do not know which one. A cheaper judge is acceptable only if it is checked, which the audit does. | The graders' judge may be stricter or more lenient. `python -m eval.audit` measures ours on four control replies per probe (GOLD should pass; WRONG and EMPTY should fail; ABSTAIN should pass only where `should` asks for "not on record") and writes `results/judge_audit/audit.md`, so its error rate is measured rather than assumed. `audit.jsonl` is append-only: a rerun judges only the cases it does not hold yet. |
| B5 | **The 8,000-token cap is enforced before each reply call, with a local count.** We count with the Qwen3 tokenizer that ships in `pilot/data/`, plus 7 tokens per message and 10 per prompt for the chat template (`pilot/tokens.py`). The prompt builder aims at 7,400 (`target_input_tokens`), and a request whose local count is over 8,000 is never sent (`TOO_BIG`). `Reply.input_tokens` is the provider's own count for that call (ours if it reports none, 0 if no call was made). | The cap has to hold before sending, but the provider reports its count only afterwards. A live check: 1,977 local vs 1,973 reported on a ~2,000-token prompt. In the exploratory baseline run (1,575 reply calls, older code) the provider was never more than 7 tokens above our count, except on `own_02`'s 13k-token paste: 7,660 reported vs 7,342 local (+4.3%), still under 8,000. | Model ids starting with `qwen/` are assumed to use this tokenizer (factor 1.0). Any other model is counted ×1.25 (`UNKNOWN_FACTOR`), which keeps a tokenizer up to about 1.35× as heavy as Qwen3's under 8,000 at the 7,400 target. After each call, `observe()` raises the factor (never lowers it) when the provider counted more than we did by over max(20 tokens, 1%), and saves it in `<data_dir>/token_calibration.json`, so a restart keeps it. A first reply on a heavier tokenizer (over 1.35×, or over about 8% for a `qwen/` model) could still exceed 8,000 before the factor is learned. If the tokenizer cannot load, a pessimistic 3-bytes-per-token estimate is used. |
| B6 | "Input tokens" means the whole request the provider bills: system prompt, notes, history, the current message and the chat-template tokens. | That is what "at most 8,000 input tokens" means operationally, and it is the number the provider reports. | If chat-template tokens did not count, we are simply about 1% conservative. |
| B7 | Helper calls (extraction) do not count toward the 8,000 limit. Their token usage and cost are reported separately (the helper columns of each report). | The brief says so. | None. |
| B8 | **Spend is the sum of the costs the provider reports per call** (`usage.cost`): reply and helper calls from each system's `usage.jsonl`, the judge's votes (including attempts that gave no verdict), and job attempts that `--resume` replaced (`eval/report.py: spend`). The key's usage counter, read before and after a run, is printed only as a cross-check. | It is exact, per call and in USD, and the spend line is then the sum of the report's own tables. The key counter lags, misses judging done later with `eval.judge`, and counts any other use of the key. | A provider that sends no `usage.cost` would show $0, and spend would have to come from its billing page. The judge audit's cost is in `audit.md`, not in a run's spend line; the day's total adds development, every run and the audit. |
| B9 | **The API key is in the environment when `chat()` runs.** `pilot` reads the variable named by `api_key_env` at every call (so it may be set after the `Assistant` is built), strips stray whitespace, and redacts the key from every error. `pilot` never reads `.env`; only the eval scripts load it (python-dotenv, which never overrides a variable that is already set). | The brief's `config` names an environment variable, and the graders bring their own key. A stray space or CR in the variable made the Authorization header illegal, and the HTTP library's error quoted the header, key included. | If the graders expect `pilot` to load `.env` itself, every reply is the fixed `FALLBACK` text with `input_tokens` 0 (each message is still saved). One `load_dotenv()` call in `Assistant.__init__` would fix that. |

## C. Users, accounts and conversations

| # | Assumption | Why | If wrong |
|---|---|---|---|
| C1 | **Only the user's own words become memory.** Pilot's replies are stored in the log and shown in the session tail, but never indexed, shown in TODAY or turned into notes. | Complaint 6 ("a confident date I never mentioned") gets worse if a system re-reads its own guesses as facts. Keeping user statements and model output apart gives every note a trustworthy source. | Users who expect Pilot to recall its own earlier drafts across sessions lose out (scenario `own_11` measures this). The fix would be to store drafts as artifacts linked to the request, kept separate from facts. |
| C2 | **Pasted assistant turns are not the user's words** (`pilot/text.py: strip_pasted_assistant`). In a pasted transcript, an AI turn starts at a line labelled Pilot:, Assistant:, AI:, Bot:, ChatGPT:, Claude: or Copilot: ("ChatGPT said:" too) and runs until a line labelled as the human (Me:, User:, You:, Human:, I:), another AI label, or the end of a "> " quoted block. Other labels ("Summary:", "Next Steps:", "Maya Lopez:") never end it. Text counts as a transcript only when it has both an AI-labelled and a human-labelled line. The AI turns are left out of memory (search, TODAY, extraction); the message itself is saved and sent whole. | Complaint 3 describes users pasting old chats. Assistant replies are full of headers and names; when those counted as a new speaker, the rest of the reply, an invented date included, was stored as the user's own words. Requiring both kinds of label keeps a user's own note such as "Pilot: started 3 March" from being stripped. | Pastes in other formats are indexed in full, so some assistant text can become searchable. The other way round, the user's own lines inside an AI turn that carry no human label are left out of memory (they stay in the log and in that turn's prompt). |
| C3 | **We learn accounts from what the user writes.** There is no CRM and no list of accounts. An account exists once the helper proposes it and its name appears in the message (pasted AI turns removed). An alias the helper proposes is kept only if the message uses it. | The brief gives no account list. AMs name their accounts constantly. | An account the helper never proposes gets no card; its messages are still in keyword search. With a CRM feed, accounts and aliases would be seeded from it, which is more robust for nicknames. `lex` has no extractor, so it has no accounts at all. |
| C4 | **A message that names no account (and no known contact) continues the accounts of the latest earlier message in the same session that named some**, at most 3 (`pilot/context.py: accounts_in_play`). The accounts in play when a message was answered are saved with it (meta key `msg_accounts:<id>`), and extraction uses that snapshot even when it runs later. A note from such a message is filed under the continued account only if there was exactly one. | Sessions are short and focused: "draft it for her" follows "Acme's CFO…". A note extracted late (a catch-up after a failed helper call) must not land on the account the session has moved on to since. | Users who switch accounts without naming them get the previous account's card; keyword hits from other accounts are still shown, labelled with their account (C18). A note from a message that continues two accounts is rejected (`ambiguous_account`): it stays in the log and keyword search, but not on a card. |
| C5 | **Two users never share anything, enforced on disk:** one SQLite file per user under `<data_dir>/users/`, named by a hash of the user id (`pilot/store.py: user_db_name`). | It is the strongest and simplest way to guarantee the brief's rule. A shared index would even let one user's data shift another user's search ranking. | If teams later need sharing (for example an account handover), it has to be an explicit copy between users, never a shared table. |
| C6 | Timestamps are naive local wall-clock times. If a `ts` carries a timezone, we drop it and keep the wall-clock time. | The scenarios use naive ISO timestamps, and "today" means the AM's day. | With multi-timezone users, "today" and the relative dates would need the user's timezone. |
| C7 | **Relative dates are resolved by code from the message's `ts`, never by the model** (`pilot/timeutil.py: resolve_when`). "Yesterday" said on Tue 10 Mar is Mon 9 Mar 2026. "Next Thursday" is Thursday of next week, with this week's as the alternative while it is still to come. Where a reading could be past or future, the words around the phrase decide (`tense_of`: past cues such as "kicked off", "signed"; future cues such as "will", "by", "ends", "is <date>"; both or neither means no tense). A bare weekday is the coming one (today counts), or the one just gone after a past cue, with the other as the alternative. A day and month without a year is the one within the last 30 days if there is one, else the coming one after a future cue, else the nearer one. A quarter without a year is next year's once this year's has ended, unless the words are past. A weekday written with a date ("Thursday 2 April") belongs to it and can settle the year. "3/4" is left unresolved, and a lowercase "may" is the verb. A note's date comes from the helper's `when` phrase if the user wrote it (resolved by code against the quote's tense). Otherwise it comes from the first date phrase found in the quote, by rule priority, so "today" or "this morning" counts only when there is no other. The reply prompt lists what each date phrase in the new message means (up to 4, `pilot/context.py: date_hints`). | The model can't be trusted with date arithmetic (complaint 6), and ambiguity should be visible, not hidden. | The cue lists are short English word lists. A wrong rule gives a confidently wrong date that the prompt presents as computed by code, which is complaint 6 again; the bracketed alternative and the quote with the day it was said are the only guard. Teams with a fixed convention (for example "next Thursday" always means the coming one) change one rule in `pilot/timeutil.py`. |
| C8 | A week runs Monday to Sunday. "This <weekday>" is the one in the current week, "last <weekday>" the latest one before today. Business days and holidays are not modelled. | This is the usual business convention. | It only affects phrases like "next week" and "this Monday". |
| C9 | **When facts conflict, the newer one wins.** A message that says an open note is no longer true ("Ravi replaced Lena as COO") closes it through a validated `closes` entry: the note must be open, from an earlier message and of an account in play (or of none), and the closing words must be the user's own (V5). Two rules were added after the first final run, where the helper closed notes it should not have:
- A message that names an account may close only that account's notes; the accounts carried over from the session count only when the message names none. "Relecloud too: Amara takes over UAT approvals from Ben" had closed a Litware contact.
- A contact is closed only by a message that names that person.

The helper is also told that a progress update or a new figure ("9 of 12 seats active") is a new fact, not a reason to close the earlier note. The helper sees at most 40 open notes it may close, contacts and preferences first. Closes are applied before the message's new notes. A new note whose quote contains an open note's whole quote and more replaces it; a new quote already contained in an open note is a repeat and is not stored (V4). Closed notes stay on the card under "No longer true" (at most 3), with their computed date, instead of being deleted: "the pilot kicked off yesterday" still dates the kickoff after a later note replaced it. | Stale facts are a quieter version of complaints 1 and 5. Keeping the old note visible but marked lets the model explain what changed. Closing first stops the replacement being dropped as a repeat of the note it replaces. | Containment is exact after `norm()` (case, spacing, curly quotes), so a reworded or re-punctuated update ("…one-page summary." then "…one-page summary plus an annex.") leaves both notes open, and the memory guide's "between two notes, the newer one wins" has to settle it. If users want a hard delete ("forget that"), add a delete path. The design supports it, because notes point to the messages they came from. |
| C10 | English only. | The brief and the users are English-speaking. | The FTS5 stemmer (Porter), the stopwords, the company-suffix list, the tense cues and the date patterns are English-specific (the tokenizer is not). Another language would need its own lists and patterns. |
| C11 | Users want short acknowledgements when they log information, and ready-to-use drafts when they ask for them. The same persona prompt is used by every variant. | This is how a busy AM works. Sharing the prompt keeps the comparison fair. | Changing the persona changes reply length, and with it how much history fits in a recency window. That is why every variant uses the same one. |
| C12 | `start_session` and `end_session` only do bookkeeping and, in `new`, catch-up extraction: each extracts up to 5 messages still pending. A reply extracts its own message, then catches up on up to 2. Nothing important waits for `end_session`. | The brief says it may never be called. A session edge suits a catch-up because no reply is waiting, and one `chat()` never works through a long backlog. | Every message is saved before the model is called, so nothing is lost. A catch-up stops at the first failed helper call, and a message is given up after its second failed call, or at once if the helper's answer is not JSON. After a long outage some messages never reach a card; they stay in the log, TODAY and keyword search. |
| C13 | Deleting or forgetting data was not required (no privacy request was given). Everything is kept. | The brief did not mention it. | A "forget" command would delete the message, its FTS rows and its notes, since every note records its source message. |
| C14 | A message too long for the prompt is cut in the middle for that reply, keeping about 55% from the start and 45% from the end, with a marker saying how many words were left out: in `new` and `lex` above 2,500 tokens (`CURRENT_MAX`), and any tail turn above 700. A run of over 100 characters without spaces (a URL, base64) counts as one word per 100 characters, so it can be cut too. The message is still stored and indexed in full. The baselines cut the current message only when it cannot fit beside the system prompt. | The 8,000 limit has to hold even for a 13k-token paste. The start says what a message is about, and the end usually holds the question. | A question buried in the middle of a giant paste gets a weaker answer on that first turn only. |
| C15 | **A note belongs to the account the user's words tie it to; code checks the helper's choice** (V2, `pilot/extract.py: resolve_account`). The helper's account is accepted when it is the only account the message names (by name, alias or a contact's full name). When several are named, it is accepted only if the quote's own sentence names it, or, when that sentence names none, it is the account named last before the quote ("Just off a call with Acme. Their CFO wants…"), or the note's person is its contact. A person the user names who is an open contact of exactly one account takes the note there when the helper proposes that account or none, unless the quote's sentence names only other accounts. With no account named, the note goes to the account in play when the message was answered, only if there was exactly one (C4). Anything else is rejected (`ambiguous_account`, `account_not_in_message`, `unknown_account`). | Complaint 5 is a fact filed under the wrong client. A rejected note is still in the log and keyword search; a misfiled one is shown as fact on the wrong card. Call notes name a client once and then talk about it. | Code never guesses, so a note the helper leaves unassigned in a message naming two accounts is lost from the cards unless its person settles it. If the helper picks the only account the message names for another account's contact ("Globex QBR is Thursday. Also Dana pinged me…"), the note is filed under Globex. |
| C16 | **People shorten company names.** `add_account` also registers the name without its generic ending as an alias (`pilot/store.py: short_name`, `COMPANY_SUFFIXES` such as Healthcare, Inc, Ltd, Partners, Airlines): "Lamna Healthcare" gives "Lamna", "Proseware, Inc." gives "Proseware". It does not when fewer than 4 letters or a stopword would be left, or another account already uses that name. Such a guessed short name counts only when written with a capital (C17). The helper is also asked for the short form the user would type next time (kept only if the message uses it, C3). | AMs drop "Healthcare" or "Inc." when they talk ("Lamna's head of IT"). Before, such an account was found only by its full name, so its card never reached the prompt (complaint 1). | A nickname that is not a cut ending ("WWI" for Wide World Importers) is found only once the user has written it in a message the helper read. A short name that is an ordinary word still matches at the start of a sentence ("Summit planning is next week" puts Summit Partners in play). |
| C17 | **A capital letter marks a name.** A guessed short name, a one-word account name or alias, and a contact's first name on its own count only when written with a capital, unless the message has no capitals at all; people's full names and other multi-word names match in any case (`pilot/text.py: mentions_capitalised`, `pilot/context.py: named_accounts`). First names shorter than 3 letters or that are common words ("Will", "May") never count alone. | Names that are ordinary words ("Umbrella", "Summit", "Mark") match ordinary sentences once case is ignored ("an umbrella agreement", "please mark the QBR"), which put the wrong client in play (complaint 5). Someone who types capitals at all capitalises names. | A user who writes names in lowercase inside otherwise capitalised text loses those mentions. A user who types everything in lowercase gets the old behaviour back, ordinary-word matches included. |
| C18 | **A keyword hit is labelled with the account(s) it is about**: the accounts of the notes extracted from that message, else the accounts its text names (`pilot/store.py: accounts_for_message`). Hits only about accounts not in play go last, so the gate cuts them first. | An unlabelled snippet about one client was read as being about another (complaint 5). The validators have already checked each note's account, so the notes are the best label. | A message about two accounts with notes for only one gets only that label. `lex` has no accounts, so its hits carry no labels. |
| C19 | **A capitalised word the user never wrote before is not on record.** When keyword search finds something, each word the new message writes with a capital that is not an account name or alias, a contact's name or a date word, and that no earlier user message contains (one FTS5 term at a time, stems matching), is listed: "Nothing on record mentions: Brightwater." When search finds nothing at all, one line says so instead ("Keyword search of earlier notes found nothing for: …"). The check answers "on record" whenever it cannot run (`pilot/store.py: term_on_record`). | Search ORs its terms, so a question about a client never mentioned still gets hits on "pilot" and "start", and the model was shown another client's start date (complaint 6). "Not on record" is a claim, so it is made only when the search ran and found nothing. | A capitalised ordinary word the user never used before ("Honestly, …") is listed too: noise, not a false fact. A name the user gave only inside a pasted AI turn is not on record, by design (C2). |
| C20 | **A follow-up more than 14 days past its date is history**: it leaves the card (an undated one counts from the day it was said). Follow-ups take at most 30% of a card. Card items go in priority order (people, preferences, follow-ups, facts, no longer true), newest first within each; an item that does not fit is skipped and later ones still get their chance. Cards share 2,400 tokens, at least 700 each. | Open follow-ups never expire otherwise: on a busy account, months-old ones filled the card until no fact was left. | An overdue to-do that is still open, or an undated one older than two weeks, vanishes from the card. It is still in the log and in keyword search. |
| C21 | **A note with no account is kept only as the user's own general preference.** It is shown in every `new` prompt ("General preferences"), so it is stored only when no person is grounded in it ("I prefer bullet points"). A fact, follow-up or contact with no account is not stored. | A wish of a person the user named is a client contact's, and applying it to every account was wrong. A fact with no account has no card to sit on. | A user's own rule that names a person ("send Priya and me bullets") is rejected. An unattributed client wish without a person ("they want bullets", with no account in play) becomes a rule for every account. All of them stay in keyword search. |
| C22 | **A person named with a role is a contact**, even when the helper filed the sentence only as a preference or a fact ("Their CFO, Jane Doe, wants …"): code adds the contact. A name or a role is kept only if a word of it (3+ letters) is in the user's words, or the person is already a contact of that account (V6). | Complaint 2 ("re-explain who is who"): the People line and first-name lookups need the contact, and the helper often reports only the wish. | A role mentioned in passing becomes a People line, and a role the helper expanded ("Chief Financial Officer" from "CFO") is dropped. |
| C23 | A message with fewer than 2 content words ("ok thanks", "Signed!") holds nothing worth a helper call. | Content words are what search indexes: 3+ letters (or 2 with a digit), not stopwords. "Jane left Acme." has three and retires a contact. | A one-content-word fact is not extracted. It is still in the log, TODAY and keyword search. |
| C24 | **The harness may pass ids and text that are not clean strings.** Ids are taken as `str()`, so 7 and "7" are the same user. A lone surrogate (half an emoji) is saved as "?" in a message, is escaped in a session id so two ids never merge, and is kept when a user id is hashed. | The brief types them as `str`, but a generator that slices UTF-16 can cut an emoji in half, and SQLite rejects such text: the message was neither saved nor answered. | A harness that treats 7 and "7" as different users would see them merged. |
| C25 | **One call at a time per instance, and one live instance per `data_dir`.** Each public method holds the instance's re-entrant lock, and the SQLite connection may be used from any thread (`check_same_thread=False`). A dropped instance closes its files in `__del__`, because the harness's restart drops it without `close()`. | A harness may run each call on a worker thread (a per-call timeout); with SQLite's default, every such call answered "couldn't save". On Windows an open SQLite file cannot be deleted, so a harness that deletes `data_dir` after a scenario failed. | Concurrent calls on one instance are serialised, not parallel. Two live instances on one `data_dir` (two processes) are not supported: SQLite keeps each write atomic, but catch-up extraction and the token calibration file could do work twice or race. |
| C26 | **`chat()` always returns a `Reply`; when no model call produced it, `input_tokens` is 0.** Fixed texts: `FALLBACK` (provider unreachable after its retries), `TOO_BIG` (request over the cap, never sent), `NOT_SAVED` (the message could not be saved, so nothing is sent). An empty model answer becomes "(no reply text)". If the prompt cannot be built, the message goes with the persona, the grounding rules, the date line and a line saying NOTES could not be loaded. A paid reply is never turned into `FALLBACK` because a log could not be written. `start_session` and `end_session` never raise, in every variant; only the constructor raises, for an unknown `memory` mode. | The brief's replay must not stop on one failure, and "input tokens of the call that produced this reply" has no call to count. A plain message beats a guess. | A harness that treats `input_tokens` 0 as an error would see one per failure. Our eval flags these replies instead of judging them (D10). |

## D. Baseline and evaluation
